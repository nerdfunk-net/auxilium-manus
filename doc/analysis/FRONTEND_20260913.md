# Frontend Analysis — 2026-09-13

Scope: `/frontend` (Next.js 16 App Router, React 19, TypeScript, TanStack Query, Zustand,
Shadcn UI). ~676 `.ts`/`.tsx` files. This is a point-in-time static review (code reading +
`ripgrep` sweeps), not a running-app penetration test.

**TL;DR:** The authentication/token architecture, the API-proxy pattern, and the CSP/security
headers are implemented carefully and correctly — better than most production Next.js apps.
The main gaps are (1) **very widespread bypass of Shadcn UI primitives** (raw `<input
type="checkbox">` / `<input type="text">` instead of the project's own `Checkbox`/`Input`
components) across ~40 files, (2) a handful of **God components/hooks** that should be split,
(3) thin **frontend test coverage** (17 test files / ~676 source files), and (4) a few minor
CLAUDE.md rule-2 (memoized hook returns) inconsistencies that are currently harmless but are
exactly the pattern the rule exists to prevent. No secrets, tokens, or credentials are exposed
to `localStorage`/client JS; no `dangerouslySetInnerHTML`/`eval`; no direct-to-backend fetches.

- Raw `<input type="checkbox">` appears in **41 files**, vs. the Shadcn `Checkbox` import in
  only **13 files**:

```338:338:frontend/src/components/features/workflow-steps/run-command/index.tsx
            type="checkbox"
```

  Examples span almost the entire `workflow-steps/*` catalog (`run-command`, `merge-content`,
  `compare-data`, `deploy-rendered-template`, `update-attribute`, `store-artifact`,

- Raw `<input>` text fields (48 occurrences total) also bypass `Input` in several places,

  the username/password fields are plain `<input>`, not `<Input>`), and two raw `<textarea>`

Impact: inconsistent focus rings/keyboard nav/disabled styling vs. the rest of the app,
duplicated Tailwind utility strings instead of one themeable component, and it makes a future
design-system change (e.g. a new checkbox indeterminate state, or RTL/accessibility fix) a

(pre-Shadcn-adoption) pattern for `workflow-steps/*` that was never migrated once `ui/checkbox.tsx`
landed — worth a dedicated cleanup pass (a good `refactor-cleaner` task: codemod every
`<input type="checkbox" checked={x} onChange={e => f(e.target.checked)} className="size-4 ...">`
to `<Checkbox checked={x} onCheckedChange={f} />`).

**1b. A large Zustand store with several unrelated responsibilities.**

`use-workflow-builder-store.ts` (318 lines) is a single store combining: workflow *metadata*
(name/description/folder/visibility), canvas *UI* state (right-panel tab, selection,
snap-to-grid, grid visibility), cross-route *navigation intents* (`pendingWorkflowLoad`), and
an in-memory *unsaved-draft* singleton (`canvasDraft`) with per-user reconciliation. Each piece
is well-commented and individually justified, but bundling all four into one store means any
component that needs e.g. `snapToGrid` re-renders on unrelated `workflowName` churn unless it
uses a fine-grained selector everywhere (which it mostly does — no evidence of the anti-pattern
biting yet). Recommend splitting into `useWorkflowMetadataStore` / `useCanvasUiStore` /
`useCanvasDraftStore` next time this file is touched, rather than growing it further.

## 2. Security review

### ✅ Strong points

- **No client-exposed secrets.** No `NEXT_PUBLIC_*` env vars at all; `process.env` is only read
  server-side (`api-proxy.ts`, route handlers, `middleware.ts` for `NODE_ENV`).
- **Auth token never touches client JS.** The JWT lives only in an `httpOnly`, `sameSite=lax`,
  `secure`-in-prod cookie (`AUTH_COOKIE_NAME`, `lib/auth.ts`). `auth-store.ts` (Zustand) holds
  only the *user profile* (`AuthUser`), never the token. No `localStorage`/`sessionStorage` use
  for tokens anywhere (`sessionStorage` is used only for the OIDC `state` nonce and a
  `resizable-split` panel-width UI preference — both appropriate, non-sensitive uses).
- **Proxy hardens the request/response boundary** (`lib/api-proxy.ts`):
  - Strips `authorization`/`cookie` from the *inbound* browser request before forwarding
    (`STRIP_REQUEST_HEADERS`) — a compromised/XSS'd page can't smuggle a different bearer token
    or exfiltrate the cookie via the proxy.
  - Strips `set-cookie`/`location` from the *backend* response (`STRIP_RESPONSE_HEADERS`) with a
    documented rationale: the server-side fetch to the backend uses `redirect: "manual"`, so a
    backend 3xx is never blindly followed by the browser's own `fetch` (which defaults to
    `follow`).
  - `normalizeProxyPath` rejects `.`/`..`/empty path segments (path-traversal guard) and
    percent-encodes each segment individually before composing the backend URL, with a
    documented reason (a literal `#` must not become a URL fragment and silently truncate the
    query string).
  - Backend connect failures return a generic `503 {"message": "Backend unavailable"}` —
    exception details never leak to the client, consistent with the `safe_http_errors` policy
    on the backend side of the house.
- **CSP + security headers are genuinely well-built**, not boilerplate:
  - `middleware.ts` generates a **per-request nonce** via `crypto.randomUUID()`, sets
    `script-src 'self' 'nonce-{nonce}' 'strict-dynamic'` (tightened to drop `'unsafe-eval'`
    outside development, with a one-line justification comment for why dev needs it), and
    `object-src 'none'`, `frame-ancestors 'none'`, `base-uri 'self'`, `form-action 'self'`.
  - The nonce is correctly wired: `x-nonce` request header → read in `app/layout.tsx` → applied
    to Next.js's own inline bootstrap scripts. This is the step most Next.js CSP setups get
    wrong (setting a nonce in middleware but never plumbing it to `<Script nonce>` /
    `layout.tsx`), and it's done correctly here.
  - `next.config.ts` adds `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
    `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy` (camera/mic/geo
    off), and HSTS in production.
  - `style-src 'self' 'unsafe-inline'` is the one CSP relaxation — standard for Tailwind (no
    inline-style avoidance layer in place) and low severity, but worth knowing it's there.
- **No `dangerouslySetInnerHTML`, no `eval(...)` in app code.** `react-markdown` is used without
  `rehype-raw`/`rehype-sanitize`, so raw HTML in Markdown source is escaped, not rendered — safe
  by default for the one Markdown-preview surface (`markdown-editor.tsx`).
- **CSRF is mitigated in depth**: `sameSite=lax` on the auth cookie means a cross-site POST
  (the classic CSRF vector) does not attach the cookie at all; on top of that the backend's
  actual authorization boundary is a bearer token the proxy injects server-side from that
  cookie, never a token the browser sends directly — a forged cross-origin form post has no
  cookie and thus no way to reach an authenticated backend call.
- **OIDC state/CSRF handling** (`lib/oidc-state.ts`) validates presence, exact match against the
  value stashed in `sessionStorage` before the redirect, and a provider-id shape check on the
  `providerId:nonce` composite state — consistent with the backend's PKCE + nonce hardening
  documented in CLAUDE.md.
- **Frontend permission checks are explicitly documented as UX-only**, not a security boundary:
  `lib/permissions.ts` opens with *"Frontend-only UX gating. The real security boundary is the
  backend's `require_permission` dependency."* — the correct mental model, and it's rare to see
  it spelled out this clearly in comments.
- **5xx bodies are truncated defensively** even though the backend already sanitizes them
  (`use-api.ts::buildApiErrorMessage` caps any ≥500 message to `MAX_ERROR_MESSAGE_LENGTH` = 300
  chars) — a good belt-and-suspenders move given `core.safe_http_errors` lives in a different
  codebase/deploy unit.

### ⚠️ Findings

| Severity | Finding |
|---|---|
| Low | **`Math.random()` for toast IDs** (`hooks/use-toast.ts:36`): `Math.random().toString(36).substring(2, 11)`. Not a security issue (it's a UI dismiss key, never sent to a server or used for anything auth-related), but it's the kind of thing that gets copy-pasted into a security-relevant context later. If any future code reuses this pattern for a client-generated *nonce/id that crosses a trust boundary*, it must switch to `crypto.randomUUID()` (already used correctly in `middleware.ts`). |
| Low | **CSP `style-src` keeps `'unsafe-inline'`.** Necessary for Tailwind's current setup, but it does mean a script-injection bypass isn't needed for a pure CSS-based attack (e.g. CSS-exfiltration via `input[value^=]` selectors) — very low practical risk for this app's data shape, noted for completeness. |
| Low | **`login-page.tsx` uses raw `<input>` rather than the shared `Input`** — no functional/security impact, but it means this one surface didn't inherit whatever hardening (e.g. consistent `maxLength`, autocomplete attributes) gets added to `Input` centrally in the future. `maxLength`/`autoComplete` are currently hand-duplicated correctly here, but that's exactly the kind of duplication that drifts. |
| Info | **No client-side rate limiting / lockout UI** for repeated failed logins — acceptable since the backend enforces the real limits (`LoginRateLimiter`, per CLAUDE.md), but a UX opportunity (e.g. surfacing "too many attempts, wait Ns") is currently just a generic "Invalid username or password" on 429 (`app/api/auth/login/route.ts` maps 401 *and* 429 to the same message) — arguably fine for not leaking rate-limit state, but slightly confusing for a legitimately locked-out user. |

No instances of: hard-coded secrets/API keys, `innerHTML`/`outerHTML` assignment, unsanitized
`window.location` redirects from user-controlled input (the two `window.location.assign(...)`
calls use a `authorization_url` returned by the *backend*, not a client-controlled query
param), or npm packages with obviously risky patterns beyond the two known/overridden
transitive CVEs already pinned in `package.json` `overrides` (`dompurify`, `postcss`, `sharp` —
none of which are imported directly by app code, confirming these are deliberate transitive
version pins, not new attack surface).

## 3. Token management — deep dive

Flow: `POST /api/auth/login` → backend issues `{access_token, expires_in}` → Next.js route
sets the `httpOnly`/`sameSite=lax`/`secure`(prod) cookie with `maxAge = expires_in` → every
subsequent `useApi().apiCall()` goes through `/api/proxy/*`, which reads the cookie
server-side and injects `Authorization: Bearer <token>` → backend validates as normal.

### ✅ Correct design choices

- **Token is never readable by page JS** (httpOnly) — immune to a garden-variety XSS token
  theft, which is the #1 reason to avoid `localStorage` JWTs.
- **`use-session-manager.ts`** implements a sensible idle-timeout + sliding-refresh model:
  - Refreshes every 15 min while the tab is active (`refreshInterval`), checked every 60s
    (`checkInterval`), and force-logs-out after 20 min of *no user interaction*
    (`idleLogoutTimeout`), tracked via `mousedown/mousemove/keypress/scroll/touchstart/click/focus`
    listeners (passive, so no scroll-jank).
  - `isRefreshingRef` guards against overlapping refresh calls (no thundering-herd of parallel
    `/api/auth/refresh` requests if the interval fires while one is in flight).
  - On a `401` from refresh, forces logout and clears TanStack Query's cache
    (`queryClient.clear()`) — explicitly called out in a comment as intentional so cached
    device configs / run output can't survive in memory for "the next person on a shared
    machine," a real (kiosk-style NetDevOps workstation) threat model for this app.
  - Uses a **soft** `router.replace()+router.refresh()` on forced logout rather than a hard
    reload, specifically to preserve the in-memory `canvasDraft` singleton so a user's unsaved
    workflow survives an idle-timeout logout/re-login — a subtle, well-thought-through UX/security
    tradeoff (the draft is pinned to `userId` and wiped by `reconcileDraftOwner` if a *different*
    user logs in on the same tab afterward, so this doesn't leak drafts cross-account).
- **`/api/auth/refresh` and `/api/auth/me` both clear the cookie** on a 401/403 from the backend
  (`clearAuthCookie`), so a revoked/expired token can't linger client-side as a stale cookie
  that keeps getting sent.
- **Every auth route validates the backend response shape before trusting it**
  (`parseTokenResponse`/`parseSessionResponse`/`parseAuthUser` all narrow `unknown` → typed,
  returning `502` on a malformed body) — defends against a misbehaving/mismatched backend
  silently corrupting the session cookie.
- **`useApi()` centralizes 401 handling**: any proxied call that 401s redirects to `/login`
  immediately, so an expired/revoked token can't leave the UI in a stuck "loading forever" state.
- **`must_change_password` forced-flow is respected client-side**: `buildApiErrorMessage`
  recognizes the `password_change_required` code on *any* 403 (not just a hardcoded list of
  endpoints) and flips the flag on the already-loaded user via `onPasswordChangeRequired()`
  rather than waiting on the next poll — matches the backend contract described in CLAUDE.md.

### ⚠️ Flaws / risks worth knowing about

| Severity | Finding | Detail |
|---|---|---|
| **Medium** | **Refresh cadence vs. idle-timeout ordering can race on the very first check tick after 15 min if a tab is backgrounded (`setInterval` throttling).** | Browsers throttle/suspend `setInterval` timers in backgrounded tabs. If a tab is backgrounded for >20 min then foregrounded, `lastActivityRef`/`lastRefreshRef` are stale by the throttled amount; the *first* tick after resuming can immediately fire `forceLogout("idle")` even though the user just interacted (the `mousedown` that refocused the tab needs to land *before* the stale interval tick fires, which isn't guaranteed). This is a UX correctness issue more than a security hole (fails safe, toward logout, not toward a stale/too-long session), but it means the effective idle timeout is "20 minutes of foreground activity, ± whatever the browser throttled the background tab by" rather than a hard 20-minute wall-clock guarantee in either direction. Consider re-checking `document.visibilitychange`/re-stamping `lastActivityRef` on tab focus before the next interval tick. |
| **Low** | **No token-rotation-on-refresh visibility check for concurrent tabs.** | Each tab runs its own `useSessionManager` instance with independent `lastRefreshRef`/`isRefreshingRef` (they're `useRef`, not shared/broadcast across tabs via `BroadcastChannel`/`storage` events). Two tabs open on the same session will each independently call `/api/auth/refresh` on their own 15-minute clocks — harmless functionally (the backend just re-mints a token each time, and every tab's cookie write is to the same `httpOnly` cookie so they don't fight), but it is 2× the refresh-endpoint traffic per open tab, and if the backend ever moves to single-use refresh tokens (rotation-on-use) this pattern would start invalidating sibling tabs. Not a problem *today* given the backend's bearer-token model (CLAUDE.md: refresh just re-mints from `tv`+`sid_iat`, not a rotating refresh-token), but worth a `BroadcastChannel`-based "leader tab" refresh if the backend model changes. |
| **Low** | **`expires_in`-derived cookie `maxAge` vs. `SESSION_MAX_AGE_HOURS`.** | The cookie's `maxAge` tracks the *access token's* `expires_in` (short-lived, refreshed every 15 min client-side), not the backend's absolute `SESSION_MAX_AGE_HOURS` session ceiling. This is correct/intended — the cookie must expire with the token it holds — but it means the browser will keep resending an about-to-expire cookie right up to `sid_iat + SESSION_MAX_AGE_HOURS` with no client-side warning to the user that the *session* (as opposed to just the current token) is about to hard-expire; the user's first sign that the absolute session ceiling was hit is a hard 401 mid-action. A "your session ends in N minutes, save your work" banner near the ceiling would be a nice-to-have, not a flaw. |
| **Info** | **`console.error` on refresh failure** (`use-session-manager.ts:128`) logs the raw error to the browser console. It's a `catch` around a same-origin `fetch` to `/api/auth/refresh` (network errors only, never a response body), so there's no token/PII in that log — flagged only because it's the one remaining `console.*` call in non-test app code and is worth an explicit look if a future refactor pipes errors somewhere more visible (e.g. Sentry) that a user's console shouldn't get for free. |

**Overall verdict on token management: solid.** The httpOnly-cookie + server-side-proxy-injects-
Authorization-header design, combined with the idle/refresh session manager and the
must-change-password interrupt, is a well-thought-out system. The only real actionable item is
the backgrounded-tab idle-timer race (Medium); everything else is a minor robustness/traffic
nice-to-have, not a security hole.

## 5. TypeScript best practices

### ✅ Strong

- **`strict: true`** in `tsconfig.json`, no relaxations (`noImplicitAny`, `strictNullChecks`,
  etc. all on by default under `strict`).
- **Essentially zero `any`.** `rg ": any\b|<any>|as any\b"` across the whole `src/` tree returns
  **5 hits total, all inside prose/comment strings** (e.g. "Risky: *any* command…", "approval
  expire after 24h, same as *any* other run"), not a single real type escape hatch. This is
  unusually clean for a codebase this size.
- **Zero `@ts-ignore`/`@ts-expect-error`** anywhere in `src/`.
- **`unknown` used correctly at trust boundaries** — every parsed HTTP response
  (`parseTokenResponse`, `parseSessionResponse`, `parseUserResponse`, `readErrorDetail`) types
  the raw JSON as `unknown`/`Partial<T>` first and narrows with runtime `typeof` checks before
  trusting the shape, rather than casting.
- **Discriminated unions / literal types used well** for step config modeling
  (`ExecutionMode`, `ParserMode`, `BatfishQueryQuestion`, `RunMode`, `CallbackStatus` in the OIDC
  callback page) instead of bare strings.
- **`as const` used appropriately** for option arrays (`EXECUTION_MODE_OPTIONS`,
  `PREFIX_MATCH_TYPES`, `RIBS`) to get literal-type inference instead of widened `string[]`.

### ⚠️ Minor gaps

- **`Record<string, unknown>` is the dominant shape for step config** (`config: Record<string,
  unknown>`, `params: Record<string, unknown>`, `targetConfig: Record<string, unknown>`
  throughout `workflow-steps/*` and the new Batfish tab/hook). This is a deliberate, consistent
  choice (plugin configs are heterogeneous JSON blobs by nature — this mirrors the backend's
  `dict`-typed step config), and the codebase compensates well with per-field runtime guards
  (`stringField`/`numberField`/`boolField` helpers seen in both `batfish-options-tab.tsx` and
  `use-template-editor-batfish.ts` — note these two files duplicate an *identical*
  `stringField`/`numberField`/`boolField`/`applicationsField` implementation; worth hoisting to
  a shared `workflow-steps/shared/config-field-helpers.ts` or `templates/utils/` module the next
  time either file is touched). But a `Record<string, unknown>` config means a typo'd config key
  anywhere in a `ConfigPanel` is invisible to `tsc` — a per-step `zod` schema (the project already
  depends on `zod` + `@hookform/resolvers` for forms) parsing `config` once at the top of each
  panel would close this gap without abandoning the "heterogeneous JSON blob" model.
- **`eslint.config.mjs` is minimal** — just `eslint-config-next`'s `core-web-vitals` + `typescript`
  presets, no additional rules for the React-hooks-correctness patterns CLAUDE.md itself
  mandates (default-param-literal, exhaustive-deps, memoized-hook-return). `eslint-config-next`
  does include `react-hooks/exhaustive-deps` as a warning, but there's no custom rule enforcing
  "custom hooks must wrap their return in `useMemo`" (see §6) — that pattern is currently
  enforced by convention/code review only, per CLAUDE.md's own "Enforcement: ESLint rules +
  pre-commit hooks block non-compliant code" claim, which doesn't appear to be backed by an
  actual custom ESLint rule in this repo today (only the standard Next.js/React presets are
  configured). This is a documentation/tooling gap: either the enforcement rule needs to be
  added, or the CLAUDE.md claim should be softened to "code-review convention."

## 6. React / library (Next.js, TanStack Query, Zustand) best practices

### ✅ Strong

- **No `useState`+`useEffect` reimplementation of server state found for genuine server data** —
  every TanStack Query hook sampled (`use-saved-inventories-query.ts`,
  `use-nautobot-source-credentials.ts`, `use-dashboard-layout-mutations.ts`, and 69 others)
  correctly delegates fetching/caching to `useQuery`/`useMutation`.
- **No inline default-`{}`/`[]` object-literal hook return defaults causing render loops found**
  — `EMPTY_DEVICES`/`EMPTY_ARRAY`-style module-level constants are used correctly where a stable
  empty-array default is needed (e.g. `options-dialog.tsx`'s `EMPTY_DEVICES`,
  `use-saved-inventories-query.ts`'s pattern).
- **`useCallback`/`useMemo` discipline is generally good** — the new Batfish files
  (`batfish-options-tab.tsx`, `use-template-editor-batfish.ts`) are exemplary: every handler is
  `useCallback`-wrapped with correct deps, and the hook's return value is `useMemo`-wrapped with
  a complete, correct dependency array (13 items, all present) — this is CLAUDE.md's "Custom
  Hooks - Memoize Returns" rule applied exactly as documented.
- **`use-session-manager.ts`** is a good demonstration of the "exhaustive deps" rule done right —
  every `useEffect`/`useCallback` in the file lists every value it closes over, including the
  slightly unusual `finalConfig.refreshInterval`/`finalConfig.checkInterval` (destructured field
  deps rather than the whole `finalConfig` object, avoiding the "config object is a new
  reference every render" trap since `finalConfig` itself is rebuilt via object-spread on every
  render — see below).
- **Cache hygiene on logout**: `queryClient.clear()` on both manual logout and forced
  idle/expired logout, explicitly to avoid leaking cached device/run data across users on a
  shared machine — a genuinely good practice most apps miss entirely.
- **Suspense used correctly** for the one place it's needed (`OidcCallbackPage` wraps the
  `useSearchParams()`-consuming content in `<Suspense>`, which the Next.js App Router requires).
